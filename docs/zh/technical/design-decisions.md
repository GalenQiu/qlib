# 设计决策

每一节按"背景 / 决策 / 影响"记录一个决策。交叉引用指向该决策在代码中可见的文件。

---

## ADR-1: 不透明的公共类型，以及作为具名例外的值语义结构体

**背景。** 库需要 ABI 稳定性，因此调用方不能计算库所拥有对象的 `sizeof` 或成员偏移。与此同时，有少数类型存在的唯一目的就是让用户在栈上构造并把它们交出去——分配器回调表是今天唯一留存下来的例子。

**决策。** 容器类型在公共头文件中是不完整类型。`ql_vector_t` 在 [`ql_vector.h`](../../../include/qlib/ql_vector.h) 中声明为 `typedef struct ql_vector ql_vector_t;`，并且只在 `src/ql_vector.c` 中定义。用户必须构造的类型则是完整结构体，且每个这样的结构体都带有尾部的 `void* reserved[]` 字段。这条规则与这个例外写在 [CONTRIBUTING.md](../../../CONTRIBUTING.md) 规则 2 中。

**影响。** 容器可以增加、删除或重排私有字段，而不会造成 ABI 破坏。代价是控制块要多一次堆分配（`ql_vector_create()` 分配 `struct ql_vector`，元素缓冲区只在首次增长时才分配），以及用访问器取代直接读取字段。新增一个不透明容器很廉价；新增一个*暴露的*结构体则必须证明这个例外的正当性。

## ADR-2: 暴露的结构体中的 `reserved[]`

**背景。** `ql_allocator_t` 跨 ABI 按值传递，因此它的布局在发布那一刻就被冻结。否则，未来的需求（`calloc` 槽位、用于版本管理的 size 字段）将不得不引入新类型或破坏性变更。

**决策。** `ql_allocator_t` 以 `void* reserved[4]` 结尾，文档中写明"预留给未来的扩展。必须清零；不要使用它们"。新成员只会从这个数组中取用。`ql_default_allocator()` 把它们留为零，因为 `src/ql_mem.c` 中的 `ql_default_alloc` 是用指定初始化器初始化的，所以所有未列出的成员都被零初始化。注意，这里最初点名的对齐分配，最终**没有**需要槽位：见下文 ADR-13。

**影响。** 四个指针的余量（LP64 上为 32 字节）在调用时不花任何代价，却换来一条兼容的增长路径。随之而来的是两项义务：头文件声明该结构体的布局已经固定，而手工构造分配器的调用方必须把这个数组清零——部分填充的结构体是调用方的 bug，库不会去检测它。这个数组是有限的：一旦耗尽，任何进一步的扩展都需要带版本的结构体或基于访问器的接口。

## ADR-3: 分配器按值传递，并被复制进容器

**背景。** 容器在它的整个生命周期内都需要一个分配器，而不只是在创建它的那次调用中需要。两个选项是：存储指向调用方 `ql_allocator_t` 的指针，或者复制该结构体。

**决策。** `ql_vector_create()` 采用复制：`vec->alloc = alloc != NULL ? *alloc : ql_default_allocator();`。头文件声明"分配器会被复制进 vector，因此调用方的结构体不需要比这次调用活得更久"。`ql_vector_destroy()` 在释放控制块之前先把分配器复制到局部变量中，这样最后那次释放不会去读它即将释放的内存。

**影响。** 只要栈上分配的分配器活过这次 create 调用就能正常工作，这消除了一类常见的悬垂指针 bug。另一面是，之后对调用方结构体的修改——包括修改 `userdata`——对已存在的容器没有任何影响；复制只做一次，之后不再读取。复制还意味着库在正常运作期间从不解引用调用方的存储，这对把分配器放在可能被卸载的共享库中的嵌入方更友好。

## ADR-4: `NULL` 分配器表示"使用默认分配器"

**背景。** 要求每个调用点都获取并传入一个 `ql_allocator_t`，会让常见情形变得冗长，并把嵌入方推向全局变量。反过来说，库也无法隐式地凭空造出一个分配器。

**决策。** [`ql_mem.h`](../../../include/qlib/ql_mem.h) 中的每个辅助函数都接受 `const ql_allocator_t*`，而 `NULL` 经由 `ql_alloc_resolve()` 解析为内建的 libc 分配器。*非 NULL* 结构体中的三个函数指针都必须非 NULL；这一要求有文档说明，但不会被再次检查，因为这里是分配的热路径。

**影响。** `ql_alloc(NULL, 64)` 与 `ql_vector_create(NULL, sizeof(int), &v)` 读起来很自然，并让快路径少分支。代价是：部分填充的结构体属于未定义行为，而不是被诊断出来的错误——`ql_alloc_resolve()` 只检查指针是否为 `NULL`。希望拒绝部分填充分配器的调用方应当自行校验。

## ADR-5: 使用带溢出检查的乘法，而不是回绕算术

**背景。** `count * size` 是计算分配大小的标准做法，也是引入堆溢出的标准做法。`size_t` 算术会静默回绕，因此回绕后的乘积看起来像是一个很小的、可以满足的请求。

**决策。** `ql_size_mul_overflow(count, size, result)` 作为公共函数存在，并且是计算元素块大小的唯一获准方式。当 `result` 为 NULL 时它返回 `QL_ERR_INVALID_ARG`，当 `count != 0 && size > SIZE_MAX / count` 时返回 `QL_ERR_OVERFLOW`，其余情况返回 `QL_OK`；失败时 `*result` **保持不被修改**。`ql_alloc_array()`、`ql_realloc_array()` 与 `ql_calloc()` 都构建在它之上，并且 [CONTRIBUTING.md](../../../CONTRIBUTING.md) 规则 10 禁止手工计算该乘积。

**影响。** 该检查基于除法，因此每次数组分配只多一次除法——相较于紧随其后的分配器调用可以忽略。由于失败时输出不被触碰，调用方可以只初始化一次自己的变量，并依赖该值要么正确、要么未被触碰，绝不会是回绕后的一半结果。计数为零的情形被显式豁免（`count != 0`），因为 `0 * anything` 合法地等于 `0`，而元素大小为 `SIZE_MAX`、计数为零时不应被报告为溢出。

## ADR-6: 辅助函数既返回 `NULL`，也上报错误

**背景。** 分配辅助函数在失败时必须返回某个东西。库同时提供错误回调，两套机制存在重叠。

**决策。** 辅助函数返回 `NULL`——"没有块"唯一合理的哨兵值——并在返回之前独立地调用 `ql_err_raise()`。`ql_alloc()` 与 `ql_realloc()` 上报 `QL_ERR_NOMEM`；数组辅助函数与 `ql_calloc()` 上报 `QL_ERR_OVERFLOW`。`ql_realloc()` 记录 libc 语义：失败时原块保持不动，且仍归调用方所有。未安装回调时 `ql_err_raise()` 是空操作。

**影响。** 调用方可以自行选择风格：检查指针，或在回调中集中记录日志，或两者兼用。有两点影响需要说明。第一，如果调用方对两者都做出反应，失败就会被报告两次，因此应当由回调负责记录、由调用方负责分支，而不是反过来。第二，所有数组辅助函数上报的都是同一条笼统消息（例如 `"ql_calloc: element count overflows size_t"`），所以这条消息只能指出是哪个操作，而不是调用方的哪个变量——分配时刻的上下文必须来自回调自身捕获的状态。

## ADR-7: `ql_strerror()` 对所有取值都有定义，其 switch 没有 `default:`

**背景。** `ql_strerror()` 接受一个枚举，但该值可能来自枚举范围之外——被破坏的结构体、从其他 API 返回的 `int` 强转而来、由比调用方头文件更新的库版本写入的值。

**决策。** 该 switch 列出了全部十四个枚举项，并且**没有 `default:` 分支**；它之后紧跟一句 `return "unknown error";`，且该函数有文档保证永不返回 NULL。没有 `default:` 是刻意的，并在 `src/ql_common.c` 中有注释说明：当新增枚举项却忘了在这里处理时，它会让 `-Wswitch`（`-Wall` 的一部分）使构建失败。

**影响。** 该函数对所有取值都有定义——没有调用方需要做 NULL 检查——并且新增错误码会产生编译错误，而不是静默的 "unknown error"。代价是字符串构造器的 switch 必须靠人工保持穷尽，而且 `-Wswitch` 只保护开启了警告的构建；是 CI 中的 `QLIB_WERROR=ON` 把这一提醒变成了硬性失败。

## ADR-8: 直接使用 `EAGAIN` 与 `ENOTSUP`，而不是通过它们的别名

**背景。** POSIX 定义了一些与其他常量取值相同的别名：在 glibc 上 `EWOULDBLOCK == EAGAIN`、`EOPNOTSUPP == ENOTSUP`。`ql_ret_from_errno()` 本可以合理地接受两种拼写。

**决策。** 只使用主名称；`EWOULDBLOCK` 与 `EOPNOTSUPP` 被刻意从 `src/ql_common.c` 的 switch 中省略，原因记录在该文件的一条注释里。

**影响。** 在同一个 `switch` 中写出某个别名的两种拼写，会产生两个取值相同的 `case` 标签，这是编译错误而非警告——因此在两者相等的任何平台上，都不可能"为了完整"而加上别名形式。不过行为本身是完整的，因为别名就是同一个整数，会匹配主名称的 `case`。剩下的微妙之处只关乎观感：在函数中寻找 `EWOULDBLOCK` 的读者找不到它，注释正是为此而写。

## ADR-9: `push_back` 与 `insert` 会钉住与 vector 构成别名的元素

**背景。** 没有什么能阻止调用方写出 `ql_vector_push_back(vec, ql_vector_at(vec, 0))`。在这种情况下有两个操作会销毁源指针：增长会调用 `realloc`，它可能移动并释放缓冲区；而 `insert` 会调用 `memmove`，它搬移的正是正在被读取的那些字节。

**决策。** `ql_vector_pin_elem()` 用 `ql_vector_contains()` 检测该参数——针对 `[data, data + size * elem_size)` 做范围测试。当指针位于存活中的缓冲区内部时，它分配 `elem_size` 字节的暂存区，把元素复制过去，并返回暂存指针来替代调用方传入的指针。`push_back()` 与 `insert()` 在每一条退出路径上都会释放暂存区。`ql_vector_assign()` 有一种代价更低的同型风险，它使用 `memmove` 而非 `memcpy`，因为同一缓冲区内的区域重叠是 `assign` 唯一可能制造的情形。

**影响。** 自引用调用是良定义的，而不是 use-after-free，并且有专门的测试在 `realloc` 总是移动块的分配器上运行以覆盖这道防护，使这个 bug 无法藏在一次无害的原位 `realloc` 后面。代价是每次 `push_back` 和 `insert` 都要做一次范围比较，外加仅在别名情形下的一次临时分配。该分配本身也可能失败，因此一次构成别名的 `push_back` 即便 vector 还有空闲容量，也可能以 `QL_ERR_NOMEM` 失败。

---

## ADR-10: 带显式倍增溢出分支的几何增长

**背景。** 每次 `push_back` 只增长一个元素会让追加变成二次复杂度。倍增是通常的答案，但 `capacity * 2` 本身在容量超过 `SIZE_MAX / 2` 时会溢出。

**决策。** 当 vector 没有容量时，`ql_vector_grow()` 从 `QL_VECTOR_MIN_CAPACITY`（8）开始；在 `new_capacity < min_capacity` 期间持续倍增；一旦 `new_capacity > SIZE_MAX / 2` 就停止倍增，此时它请求恰好 `min_capacity`。随后用 `ql_size_mul_overflow()` 校验字节数。

**影响。** 摊还后的追加是 O(1)。在本检出上观察到的行为：第一次 `push_back` 把容量从 0 变为 8；容量在第 8 个元素之前保持为 8，并在第 9 个元素时变为 16；`reserve(8)` 得到容量 8，随后 `reserve(4)` 仍使其保持为 8。溢出分支意味着即使 `min_capacity` 接近 `SIZE_MAX`，循环也会终止，并且失败以 `QL_ERR_OVERFLOW` 的形式浮现，而不是变成一次小分配。失败时 `vec->data` 与 `vec->capacity` 保持不动，因此被拒绝的增长绝不会丢失已有元素。倍增确实意味着相比大小精确的分配最多有 2 倍内存开销，而且容量永远不会归还给分配器——不存在 `shrink_to_fit`。

## ADR-11: `resize()` 清零填充，`clear()` 保留容量

**背景。** 调用方增长 vector 并读取新元素时，需要一个有定义的初值。与此同时，重置 vector 以便复用的调用方不希望为重新分配付出代价。

**决策。** `ql_vector_resize()` 在预留之后用 `memset` 把新暴露出来的区域清零填充；收缩只降低 `size`，把字节留在原处直到被覆写。`ql_vector_clear()` 置 `size = 0`，不触碰其他任何东西。两者都在 [`ql_vector.h`](../../../include/qlib/ql_vector.h) 中有文档说明。

**影响。** 读取由 `resize()` 得到的元素总是有定义的，这消除了一整类未初始化读取 bug，并由测试断言。`clear()` 是 O(1)，使填充/排空循环在第一轮之后不再有分配。代价是 `resize()` 会写一块调用方即将填满每个元素、本不需要写的内存，而且收缩不会降低容量，因此一个曾经容纳过一百万个元素的 vector 会一直保留那块缓冲区，直到被销毁。

## ADR-12: 删除 `ql_lock_t`，而不是只实现一半

**背景。** [`ql_common.h`](../../../include/qlib/ql_common.h) 的一个早期修订版声明了一个锁适配器（`ql_lock_t` 加上 `ql_lock_fn`/`ql_unlock_fn`），作为线程安全方面的前瞻性钩子。没有任何东西构造过它，也没有任何东西使用过它：这些类型既没有 setter 也没有实现，因此即使语义有误，也不会有编译器或测试发现。

**决策。** 这些类型被删除了。目前不存在并发容器，而一个正确的实现需要一条 POSIX 路径和一条 Win32 路径，各自都要有由线程驱动的测试——macOS 不提供 C11 的 `<threads.h>`，因此没有可用的单一可移植测试。`ql_allocator_t.reserved[]`（ADR-2）存在的意义正是让这项能力可以在不破坏 ABI 的前提下回归。

**影响。** 公共 API 中不再包含无法使用的类型，README 也不再宣传锁适配器。代价是真正失去了一项计划中的特性；当第一个并发模块落地时，必须把实现和测试一起重新引入。另一个选择——现在就把声明发出去，好让头文件"看起来完整"——被否决了，因为未经测试的跨平台线程代码比缺失的特性更糟。

## ADR-13: 对齐分配自行手工对齐，而不使用平台原语

**背景。** SIMD 缓冲区、按缓存行分隔、DMA 和按页对齐的 I/O 都需要超额对齐的内存。有三种获取方式摆在桌面上：C11 的 `aligned_alloc`、POSIX 的 `posix_memalign`，以及 MSVC 的 `_aligned_malloc`/`_aligned_free` 这一对。这三者都依赖具体平台，而且——更重要的是——它们全都完全绕过 `ql_allocator_t`，因此以那种方式得到的内存不是来自调用方的分配器，也无法通过它释放。另一个候选方案——把 `ql_allocator_t.reserved[]` 用来放一对对齐函数指针——被否决了：它把释放拆成两条路径，于是 `ql_aligned_free()` 必须拿到一个其对齐槽位与分配该块的分配器相匹配的分配器，而搞错这一点会破坏内存，而不是失败。

**决策。** `ql_aligned_alloc()` 和 `ql_aligned_free()` 被实现为分配器自身 `malloc`/`free` 之上的一条单一路径。请求通过两次 `ql_size_add_overflow()` 填充到 `size + alignment + sizeof(void*)`，地址向上取整，而分配器实际返回的指针存放在对齐地址紧前面的 `sizeof(void*)` 字节中。释放时读回该头部，并把它交还给分配器的 `free`。不使用任何平台原语，`ql_allocator_t` 保持原样。

**影响。** 每个字节仍然都经过调用方的分配器，因此规则 7 无需例外、也无需平台分支即可成立；代码在三个受支持平台上编译和行为完全一致。只有一条路径，因此永远不会出现哪个分配器可以释放某个块的问题。代价是具体且被接受的：每块浪费 `alignment + sizeof(void*)` 字节，对于它存在的目的——16–64 字节的对齐——可以忽略，而对于兆字节级的对齐则是浪费；返回的指针不是分配器的指针，因此必须用 `ql_aligned_free()` 释放，绝不能传给 `ql_dealloc()`、`ql_realloc()` 或 libc `free()`；而且没有对齐版的 realloc，因为头部使 `realloc` 无法得知大小。平台原语从未被使用，因此 `posix_memalign` 或 `_aligned_malloc` 本可提供的任何效率都被放弃了。`reserved[]` 保持原封不动，留给那些确实无法用这种方式叠加的扩展，例如 `calloc` 槽位或 size 字段。

## ADR-14: 网络模块从地址解析开始，不涉及 socket

**背景。** `QLIB_BUILD_NET` 曾经是一个什么都不构建的选项。网络模块是一项庞大的工程，而那些棘手的部分会立刻出现：socket 在 Windows 上需要按进程初始化（`WSAStartup` 是全局的，必须先于其他每一个 socket 调用，而在库内部没有自然的位置来调用它），socket 库在 Windows 上必须链接而在 POSIX 上不需要，而且几乎每个操作在各个平台上的写法都不同。因此，第一块切片必须按"它*不需要*什么"来挑选，否则它根本落不了地。

**决策。** 该模块从文本形式的 IPv4 地址处理开始：`ql_net_addr_parse()`、`ql_net_addr_format()` 和 `ql_net_addr_equal()`。没有 socket，没有平台初始化，没有需要链接的外部库，任何地方都没有 `#if defined(_WIN32)`。IPv6 文本会被识别出来并报告为 `QL_ERR_NOT_SUPPORTED`，而不是被误解析成 IPv4；`ql_net_addr_t` 存储十六个字节，因此加入 IPv6 不是 ABI 变更。地址族枚举使用 qlib 自己的取值，而不是平台的 `AF_INET`，后者在 Windows 与 POSIX 上并不相同。

**影响。** 每一条代码路径都是对字符串的纯计算，因此无需网络、对端、特权端口或超时即可测试，也不会在 CI 中变得不稳定。没有链接依赖，因此 `QLIB_BUILD_NET` 仍然只是一个源码层面的开关，该模块在三个受支持平台上行为一致。解析本身也证明值得做模糊测试：它是 qlib 中唯一把不受信任的文本转换成值的地方，`fuzz/fuzz_net.c` 检查往返不变量。代价是出现了一个名叫"网络"、目前却不打开任何 socket 的模块，这一点必须在文档中直说，而不能含糊带过。当 socket 真正到来时，它们会带来 `WSAStartup` 及其进程级生命期、一个条件化的链接依赖，以及该模块第一段真正与平台相关的代码——这是这块切片刻意留待解决的问题。

## ADR-15: 三个容器，各自回答一个 `ql_vector` 无法回答的问题

**背景。** `ql_vector` 是固定大小元素的连续数组，能满足大多数需求。再加入一个字符串、一张哈希表和一条双向链表，就有可能多出三种把同一件事做糟的方式。因此，只有在 `ql_vector` 对某个问题回答得很糟糕时，才接纳对应的容器；而每个容器都有一个设计决策，决定它是否配得上自己的一席之地。

**决策。**

*`ql_str` —— 缓冲区始终以 NUL 结尾。* 可增长的缓冲区本可以只记录长度，但那样它就成了一个元素类型为 `char` 的 `ql_vector`。让终止符始终就位，意味着 `ql_str_cstr()` 可以不经拷贝直接交给任何 C API，并且每个会修改内容的函数都会在返回前把它恢复——**包括失败路径**，这正是 `vsnprintf` 重试循环在一次被截断的尝试之后重写终止符的原因。内嵌 NUL 字节仍然会被接受，因为拒绝调用方已经持有的数据，比出现一个超过 `strlen()` 的长度更糟；长度具有权威性，头文件对此有明确说明。

*`ql_hash` —— 通用的固定大小字节键，而不是字符串键。* 以字符串为键的映射更易用，也能覆盖常见情形。它被否决，是因为它排除了整数键、复合键，以及调用方已经以字节形式持有的键，还因为它会悄悄为每个键分配一份拷贝。对固定大小的块用 `memcmp` 比较确实有真实代价，而这些代价是被记录下来的，而不是被隐藏的：带填充字节的结构体键无法使用，而 `char*` 键哈希的是指针。

*`ql_list` —— 节点句柄是 API 的一部分。* 没有稳定的句柄，双向链表不过是一个缓慢的双端队列。有了它们，它才能回答向量回答不了的问题：无论其间发生了什么，都能在常数时间内删除这个特定的元素。元素只是被拷贝进出，从不被引用，因此绝不会交出指向链表存储内部的指针——这也是元素类型的对齐无关紧要的原因。

**影响。** 这三个模块共用 `ql_mem` 的分配器约定和 `ql_common` 的错误码，因此它们像是库的其余部分，而不是三个附加物。每一个的代价都是可度量的：基准测试套件把它们与 `ql_vector` 直接对比（压入：连续数组 15 ns，每节点分配 29 ns；删除第一个元素：移动 39 ns，按句柄解链一个节点 15 ns），这让"除非确实需要，否则就用 vector"这条指引站得住脚，而不是想当然。代价是接口面积：多出三个不透明类型、三张错误码表，以及三样需要在两种语言中持续维护文档的东西。

这里没有任何一处新增依赖。`ql_hash` 内联实现 FNV-1a，而不是链接一个哈希库；`ql_list` 为每个节点分配一个块而不做池化，因为池化意味着还要测试第二套分配器策略，而分配器抽象已经允许调用方自行提供一套。

## ADR-16: socket 是阻塞的、仅支持 IPv4，并带来第一个链接依赖

**背景。** ADR-14 把 socket 排除在网络模块之外，因为它们一到来就同时带来三件棘手的事：`WSAStartup` 是进程级的，在库内部没有自然的位置可以调用它；一项在 Windows 上存在、在 POSIX 上不存在的链接依赖；以及几乎每个操作都有不同的写法。对第一块切片来说，推迟它们是正确的决定，但一个打不开连接的网络模块同样算不上完成。

**决策。** *仅 TCP、阻塞、仅 IPv4、无 DNS。* 每个 socket 调用在 POSIX 与 Win32 上都有唯一显而易见的写法，因此平台代码就留在它所适配的那些调用旁边，而不会散布到逻辑各处。`WSAStartup` 由一个一次性的 `ql_net_init()` 负责，每个 socket 调用都会自行调用它，另有一个可选的 `ql_net_shutdown()`；这里没有引用计数，因为一个可能与实际打开的 socket 脱节的计数，比一个不会脱节的标志更糟。Winsock 依赖在目标上是 `PUBLIC`，因此静态库的使用者也会链接它，而整个模块仍然位于 `QLIB_BUILD_NET` 之后，不想引入链接依赖的构建就不会得到它。

*阻塞而非异步。* 非阻塞 socket 需要线程或事件循环，而 qlib 两者都没有。引入其中任何一个是 ADR-14 刻意推迟的决策，而且它比本模块更大：异步 API 的测试故事是另一套测试故事。这也是没有 DNS 的原因：`getaddrinfo` 本身现在很容易，但域名解析属于一套关于超时与取消的策略，而本库目前还无法兑现。

**影响。** 地址这一半仍然不需要网络、不需要初始化、也不需要任何库，因此 `QLIB_BUILD_NET` 依然只是一个源码层面的开关，地址相关的测试也依然是密闭的。socket 这一半在回环上测试，不需要对端线程：内核会在 `accept()` 被调用之前就把连接完成到监听者的积压队列中，因此只要遵守顺序并设置了超时，连接—接受—发送—接收在单线程中就是确定性的。这是真正的测试，而不是 mock，而且它在编写过程中就抓出了两处违反约定的地方。

有两项代价是被记录下来的，而不是被隐藏的。第一，接收超时到期会被报告为 `QL_ERR_AGAIN`，而不是 `QL_ERR_TIMEOUT`，因为 Linux 与 macOS 对到期的 `SO_RCVTIMEO` 返回的就是这个，而没有 `poll()` 这一层就无法把它与"缓冲区已满"区分开。第二，想要 IPv6、DNS 或并发的调用方必须自己引入这些；模块会直说这一点，而不是假装它们会免费到来。

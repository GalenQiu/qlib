# Integration

## As a CMake subdirectory

Vendoring the source and using `add_subdirectory()` is the simplest option and
requires no installation step:

```cmake
add_subdirectory(third_party/qlib)
target_link_libraries(myapp PRIVATE qlib::qlib)
```

Always link the namespaced `qlib::qlib` target rather than the bare `qlib`.
The alias is what makes the target usable if qlib is ever consumed through
`find_package()` instead, and it carries the include directories and the C11
requirement.

With this route qlib's own tests are not built: `QLIB_BUILD_TESTS` defaults to
`OFF` whenever qlib is not the top level project. Set
`-DQLIB_BUILD_TESTS=ON` explicitly if you do want them.

`qlib::qlib` propagates the C standard as a usage requirement. A consumer
written in plain C89/C99 therefore still compiles the qlib headers correctly,
because the language level is a property of the target rather than of your
project.

## From an installed package

```bash
cmake -S . -B build -DCMAKE_INSTALL_PREFIX=/your/prefix
cmake --build build
cmake --install build
```

The install puts the headers in `<prefix>/include/qlib/`, the library in
`<prefix>/lib/`, and a CMake package configuration in
`<prefix>/lib/cmake/qlib/`. Consumers then write:

```cmake
find_package(qlib 0.1 REQUIRED)
target_link_libraries(myapp PRIVATE qlib::qlib)
```

Point CMake at the prefix with `-DCMAKE_PREFIX_PATH=/your/prefix`, or by setting
`qlib_DIR=/your/prefix/lib/cmake/qlib` directly.

The generated `qlibConfigVersion.cmake` uses `SameMajorVersion` compatibility,
so `find_package(qlib 0.1)` is satisfied by 0.1.x and rejected by 0.2.0. The
version is also available at build time through `QLIB_VERSION_MAJOR`,
`QLIB_VERSION_MINOR`, `QLIB_VERSION_PATCH` and `QLIB_VERSION_STRING`, and at run
time through `ql_version()`.

`cmake --install` understands a staging prefix, which is what packagers need:

```bash
DESTDIR=/tmp/stage cmake --install build
```

Uninstalling is available too:

```bash
cmake --build build --target uninstall
```

It removes exactly the files recorded in `install_manifest.txt` by the most
recent install.

## With pkg-config

An installed qlib also ships a `qlib.pc`, so non-CMake builds work as usual:

```bash
cc myapp.c $(pkg-config --cflags --libs qlib) -o myapp
```

The `.pc` file is relocatable: it derives its prefix from the location of the
file itself, so it stays correct when the package is staged with
`cmake --install --prefix` or `DESTDIR`.

## Without any build system

Copy `include/` plus the `.c` files under `src/` into your tree and compile
them. Two things to know:

- `include/qlib/ql_common.h` includes `qlib/qlib_export.h`. That header is
  generated by CMake into `<build>/include/qlib/`, so either add
  `-I<build>/include` alongside `-Iinclude`, or supply an empty replacement
  header of your own when building on a platform where no symbol export
  decoration is needed.
- On Windows, a consumer of the **static** library must define
  `QLIB_STATIC_DEFINE`. Otherwise `QLIB_EXPORT` expands to `__declspec(dllimport)`
  and the build fails. Consumers of the DLL should not define it.

## C++ consumers

The headers are wrapped in `extern "C"` and are safe to include from C++:

```cpp
#include <qlib/qlib.h>

ql_vector_t* v = nullptr;
if (ql_vector_create(nullptr, sizeof(int), &v) == QL_OK) {
    // ...
    ql_vector_destroy(v);
}
```

`QLIB_NODISCARD` maps to `[[nodiscard]]` when compiling as C++17 or newer, so
ignoring a result produces a warning in C++ too.

## What gets installed

```
<prefix>/include/qlib/ql_common.h
<prefix>/include/qlib/ql_mem.h
<prefix>/include/qlib/ql_vector.h
<prefix>/include/qlib/qlib.h
<prefix>/include/qlib/qlib_export.h      # generated
<prefix>/lib/libqlib.a                   # or libqlib.so / qlib.dll
<prefix>/lib/cmake/qlib/qlibConfig.cmake
<prefix>/lib/cmake/qlib/qlibConfigVersion.cmake
<prefix>/lib/cmake/qlib/qlibTargets.cmake
<prefix>/lib/pkgconfig/qlib.pc
```

`src/ql_internal.h` is deliberately not installed: it is the private interface
between qlib's own translation units.
